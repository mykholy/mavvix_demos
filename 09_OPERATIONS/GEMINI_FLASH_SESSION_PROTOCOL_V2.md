# Gemini Flash autonomy and context survival

- **Never pretend infinite execution.** Continue inside current attached coding session while tool limits allow. After each vertical persist status and precise pending tasks, so next Gemini session can resume without losing work.
- Read the eight demo specs before starting; when memory grows reread the relevant vertical requirements rather than summarizing away functional detail.
- Plan only one pass, then ship vertical slices; avoid repeatedly restarting architecture or replacing working code with a new generic template.
- Inspect tools and package registry before picking versions. If network/tool unavailable use already installed versions and report limitations.
- Run tests from terminal; record exact command, exit code, screenshots and logs. Never invent test passes or claim a node runtime when only a text chat exists.
- Before marking one vertical DONE, test native mobile and RTL, complete real operational journey in front of a browser, and save proof.
- When context truncated, preserve `progress/*` with (a) what files changed, (b) what worked, (c) known failures, (d) one exact next command and route, (e) outstanding acceptance boxes.
- Resource strategy: reuse validated data layer and admin primitives, but keep sector visual systems and domain components independent. Avoid generating all 8 visually then retrofitting logic too late.
- No paid tool/API accounts or external contacts without explicit user request. Screenshot and marketing recording only from site running locally after QA.
